### **3. Архитектурные решения и обоснования**

Данный раздел описывает фундаментальные решения, определяющие облик системы, и объясняет rationale (обоснование) behind them.

#### **3.1. Фундаментальные решения уровня системы**

##### 3.1.1. Микросервисная архитектура

**Выбранное Решение:** Система строится как набор слабосвязанных, независимо развертываемых микросервисов, каждый из которых инкапсулирует определенную бизнес-логику (например, управление данными, обучение, инференс).

**Обоснование:**
* **Масштабируемость:** Позволяет горизонтально масштабировать только те сервисы, которые испытывают нагрузку (например, `Predictor` для инференса), а не всю платформу целиком.
* **Гибкость технологического стека:** Позволяет использовать наиболее подходящие технологии для разных задач (Java для высоконагруженного бэкенда).
* **Устойчивость к сбоям:** Отказ одного сервиса (например, `Model Garden`) не приводит к полному останову платформы.
* **Независимость команд:** Команды могут разрабатывать, тестировать и развертывать сервисы независимо друг от друга.

##### 3.1.2. Событийно-ориентированная архитектура (Event-Driven) с Event Sourcing

**Выбранное Решение:** Взаимодействие между сервисами осуществляется асинхронно через общую шину событий (Apache Kafka). Ключевые изменения состояния системы фиксируются как последовательность неизменяемых событий (Event Sourcing).

**Обоснование:**
* **Слабая связанность:** Сервисы не знают друг о друге, они знают только  о событиях, что радикально снижает связанность.
* **Устойчивость и отказоустойчивость:** Сервисы-потребители могут обрабатывать события в своем собственном темпе и восстанавливаться с момента сбоя, не теряя данные.
* **Воспроизводимость и аудит:** Состояние системы может быть воспроизведено за любой период времени путем "воспроизведения" событий, что является мощным инструментом для отладки и аудита.
* **Поддержка сложных бизнес-процессов:** Позволяет легко описывать long-running процессы как серию событий.

**3.1.3. Единое объектное хранилище для артефактов**

**Выбранное Решение:** Все нефункциональные данные (артефакты) — датасеты, веса моделей, логи, конфиги — хранятся в едином S3-совместимом объектном хранилище (например, MinIO). Метаданные (информация об артефактах) хранятся отдельно.

**Обоснование:**
* **Масштабируемость:** S3-протокол заточен под хранение и обработку огромных объемов неструктурированных данных.
* **Надежность и долговечность:** Объектные хранилища обеспечивают высокую доступность и сохранность данных.
* **Универсальный доступ:** Артефакты доступны из любого сервиса или среды выполнения (Java-сервисы, Python-контейнеры для обучения) через стандартный HTTP API.
* **Экономическая эффективность:** Отделение "холодных" данных от дорогих вычислительных ресурсов базы данных.

#### **3.2. Решения по реализации**

##### 3.2.1. Бэкенд: Фреймворк Quarkus

**Выбранное Решение:** Для реализации Java-микросервисов выбран фреймворк Quarkus в реактивной модели.

**Обоснование:**
* **Оптимизация под Kubernetes:** Низкое потребление памяти и время старта критически важны для эффективной работы в Kubernetes и при использовании Knative для serverless-инференса.
* **Реактивная модель:** Позволяет эффективно работать с асинхронными I/O-операциями (сетевые вызовы, работа с Kafka, S3), обрабатывая больше запросов на тех же ресурсах.

##### 3.2.2. Межсервисная коммуникация: Асинхронность через Kafka

**Выбранное Решение:** Для команд (изменяющих состояние) используется асинхронная коммуникация через отправку событий в Kafka. Для запросов (не изменяющих состояние) может использоваться синхронный REST/HTTP.

**Обоснование:**
* **Согласованность eventual consistency:** Для большинства операций ML (обучение, деплой) не требуется строгая линейная согласованность. Eventual consistency достаточно и обеспечивает лучшую производительность и доступность.
* **Буферизация нагрузки:** Пиковые нагрузки на один сервис распределяются по времени для сервисов-потребителей.
* **Гибкость:** Новые сервисы могут подписаться на события без изменения кода существующих.

##### 3.2.3. Безопасность: Единый Point of Entry и OIDC

**Выбранное Решение:** Все входящие запросы проходят через API Gateway, который делегирует аутентификацию серверу Keycloak по протоколу OpenID Connect (OIDC).

**Обоснование:**
* **Централизация логики безопасности:** Упрощает управление доступом, аудит и обновление политик.
* **Стандартный протокол:** OIDC является отраслевым стандартом, обеспечивает надежность и совместимость с другими системами.
* **Изоляция внутренних сервисов:** Внутренние микросервисы избавлены от необходимости реализовывать логику аутентификации, они работают с провалидированным контекстом безопасности.

#### **3.3. Компромиссы и принятые риски**

* **Сложность операционного overhead:** Микросервисы и EventDrivenArchitecture(EDA) значительно сложнее в развертывании, мониторинге и отладке, чем монолит. **Смягчение:** Использование Kubernetes и полноценного стека observability (Grafana, Loki, Prometheus) для автоматизации и контроля.
* **Сложность обеспечения согласованности данных:** Eventual consistency может усложнить логику приложения, где требуются строгие гарантии. **Смягчение:** Четкое проектирование границ сервисов (Bounded Context), чтобы операции, требующие сильной согласованности, находились внутри одного сервиса.
* **Зависимость от инфраструктуры:** Система сильно зависит от надежности Kafka, Kubernetes и S3. **Смягчение:** Эти компоненты являются стандартом для построения отказоустойчивых систем и развертываются в отказоустойчивых конфигурациях.
