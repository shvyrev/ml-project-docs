### **7. Выбранные архитектурные решения**

Данный раздел описывает ключевые архитектурные решения, принятые при проектировании системы, их обоснование, а также рассмотрение альтернатив и компромиссов.

#### **7.1. Решения по обработке ошибок и отказоустойчивости**

##### 7.1.1. Обработка ошибок в асинхронных процессах (Kafka)

**Выбранное Решение:** Реализована комбинация паттернов **Retry Pattern** и **Dead Letter Queue (DLQ)** в соответствии с Enterprise Integration Patterns (EIP).

**Реализация:**
* Потребители Kafka автоматически повторяют обработку сообщений при временных ошибках (с экспоненциальной backoff-задержкой)
* После 3 неудачных попыток сообщение перемещается в специальную DLQ (dead-letter topic)
* Для DLQ реализован мониторинг и алертинг - операторы получают уведомления о необходимости ручного вмешательства
* Используется кастомный Kafka ErrorHandler для единообразной обработки ошибок across всех сервисов

**Обоснование:** Обеспечивает надежность обработки сообщений без потери данных, даже при временных сбоях зависимых систем.

**Компромиссы:** Требуется дополнительная инфраструктура для мониторинга DLQ и процедуры ручного восстановления.

##### 7.1.2. Система повторных попыток для Failed Jobs

**Выбранное Решение:** Используются встроенные механизмы Kubernetes для retry failed jobs combined with custom exponential backoff.

**Реализация:**
* `backoffLimit: 5` - максимальное количество повторных попыток
* `restartPolicy: OnFailure` - автоматический restart при failure
* Кастомный контроллер отслеживает статусы Jobs и применяет экспоненциальную задержку между повторными запусками
* После исчерпания лимита попыток Job помечается как Failed и инициируется процесс уведомления операторов

**Обоснование:** Нативная интеграция с оркестратором обеспечивает надежность и стандартизацию подхода.

**Альтернативы:** Рассматривалась реализация на уровне приложения, но выбранная стратегия обеспечивает лучшую интеграцию с инфраструктурой.

##### 7.1.3. Circuit Breaker для внешних вызовов
**Выбранное Решение:** Реализован паттерн Circuit Breaker с использованием библиотеки **Resilience4j**.
**Реализация:**
* Все внешние HTTP-вызовы (к S3, Keycloak, Kubernetes API) обернуты в circuit breaker
* Конфигурация: `failureRateThreshold: 50%`, `waitDurationInOpenState: 10s`, `slidingWindowSize: 10`
* При переходе в состояние "open" возвращаются fallback-ответы или meaningful ошибки
* Интегрировано с метриками Prometheus для мониторинга состояния circuit breakers
**Обоснование:** Защита системы от каскадных сбоев при недоступности внешних служб.
**Компромиссы:** Добавлена сложность конфигурации и необходимость проектирования fallback-стратегий.

#### **7.2. Управление распределенными транзакциями**

##### 7.2.1. Обеспечение консистентности в распределенных операциях

**Выбранное Решение:** Использование паттерна **Saga Pattern** с событийным подходом (Event Choreography).

**Реализация:**
* Каждая бизнес-транзакция (например, регистрация модели) разбита на последовательность локальных транзакций
* Каждый сервис после выполнения своей части публикует событие, которое запускает следующий шаг
* Реализованы компенсирующие транзакции (compensating actions) для отката изменений при ошибках
* Состояние саги отслеживается через специальные события (SagaStatusEvent)

**Обоснование:** Обеспечивает eventual consistency без необходимости распределенных 
блокировок.

**Компромиссы:** Повышенная сложность реализации и отладки распределенных workflows.

##### 7.2.2. Координация распределенных транзакций

**Выбранное Решение:** Реализована **Event-Driven Saga** с использованием Kafka как единого источника истины.

 **Реализация:**
* Каждая сага имеет correlation ID, который передается через все события
* Специальный сервис Saga Orchestrator отслеживает выполнение сложных мульти-сервисных операций
* Реализована визуализация выполнения саг в Grafana для упрощения отладки
* Используются transactional outbox pattern для гарантированной доставки событий

 **Обоснование:** Максимальная развязка сервисов при обеспечении согласованности данных.

 **Альтернативы:** Рассматривался подход с централизованным оркестратором, но выбранный подход лучше соответствует event-driven архитектуре.

#### **7.3. Версионирование API и событий**

##### 7.3.1. Версионирование REST API

**Выбранное Решение:** **Version-in-URL** подход с явным указанием мажорной версии.

**Реализация:**
*   Все эндпоинты имеют префикс `/api/v{X}/`
*   Мажорные версии (v1, v2) указывают на breaking changes
*   Минорные изменения обратно совместимы и не требуют изменения версии
*   Реализованы redirects со старых версий на новые в течение grace period

**Обоснование:** Простота понимания и использования, явное указание версии в URL.

**Компромиссы:** Требуется поддержка multiple версий API одновременно.

##### 7.3.2. Обратная совместимость событий Kafka

**Выбранное Решение:** Использование **Schema Registry** (Confluent Schema Registry) и формата **ProtoBuf**.

**Реализация:**
* Все события имеют четко определенную схему, зарегистрированную в Schema Registry
* Используется стратегия совместимости `BACKWARD` для обеспечения обратной совместимости
* Consumerы могут читать события, произведенные более новыми producerами
* Реализована валидация схем при производстве и потреблении событий

**Обоснование:** Гарантированная совместимость между различными версиями сервисов.

**Альтернативы:** Рассматривался Avro, но Protobuf проще использовать разным участникам.

##### 7.3.3. Стратегия эволюции схемы событий

**Выбранное Решение:** **Schema Evolution** с соблюдением принципов обратной и прямой совместимости.

**Реализация:**
* Запрещено удаление обязательных полей, только добавление optional полей
* Использование field defaults для обеспечения backward compatibility
* Процесс deprecation полей включает несколько стадий: marked as deprecated → log warnings → remove
* Интеграция с CI/CD: проверка совместимости схем при создании PR

**Обоснование:** Позволяет безопасно развивать систему без breaking changes.

**Компромиссы:** Ограничения на изменения схемы событий.

#### **7.4. Решения по безопасности данных**

##### 7.4.1. Шифрование данных в S3 (At-Rest Encryption)

**Выбранное Решение:** **Server-Side Encryption (SSE-S3)** с управляемыми AWS KMS ключами.

 **Реализация:**
* Все бакеты S3 создаются с включенным шифрованием по умолчанию
* Используются customer-managed KMS keys для большего контроля
* Реализована ротация ключей каждые 90 дней в соответствии с security policy
* Шифрование применяется ко всем объектам, включая метаданные

**Обоснование:** Соответствие требованиям compliance и защита данных от несанкционированного доступа.

**Альтернативы:** Рассматривалось client-side encryption, но выбранное решение проще в управлении.

##### **7.4.2. Шифрование данных в transit**

**Выбранное Решение:** **TLS 1.3** для всех коммуникаций между сервисами.
**Реализация:**
* Mutual TLS (mTLS) между сервисами внутри кластера через service mesh (Istio)
* TLS терминация на ingress controller для внешнего трафика
* Сертификаты управляются через cert-manager с автоматическим renewal
* HSTS заголовки для обеспечения обязательного использования HTTPS

**Обоснование:** Защита данных от перехвата и обеспечение конфиденциальности.

**Компромиссы:** Накладные расходы на шифрование/дешифрование трафика.

##### 7.4.3. Управление секретами с помощью OpenBao

**Выбранное Решение:** Централизованное управление секретами через **OpenBao** с динамическими секретами.

**Реализация:**
* OpenBao развернут в high-availability mode
* Динамические секреты для доступа к S3, БД и другим внешним системам
* Интеграция с Kubernetes через vault-agent-injector для автоматического внедрения секретов
* Автоматическая ротация секретов с коротким временем жизни
* Подробное аудит-логирование всех операций с секретами

**Обоснование:** Максимальная безопасность за счет короткоживущих секретов и детального аудита.

 **Альтернативы:** Рассматривались Kubernetes Secrets и внешние системы типа Azure Key Vault.

#### **7.5. Управление ресурсами и мультитенантность**

##### 7.5.1. Изоляция ресурсов между пользователями

**Выбранное Решение:** **Kubernetes Namespaces** как граница изоляции + resource quotas.

**Реализация:**
* Каждый пользователь/tenant получает выделенный namespace
* Resource quotas ограничивают CPU, memory, GPU потребление per namespace
* Network policies ограничивают сетевую коммуникацию между namespace
* RBAC правила обеспечивают доступ только к собственным ресурсам

**Обоснование:** Простая и эффективная изоляция на уровне инфраструктуры.
 
**Компромиссы:** Накладные расходы на управление множеством namespace.

##### 7.5.2. Квоты на использование ресурсов

**Выбранное Решение:** Иерархическая система квот с приоритетами.
**Реализация:**
* Уровни квот: organization → team → user
* Приоритизация: гарантированная квота (guaranteed) + burstable квота
* Динамическое перераспределение неиспользуемых ресурсов
* UI для запроса увеличения квот с approval workflow

**Обоснование:** Справедливое распределение ограниченных ресурсов (особенно GPU).  

**Альтернативы:** Рассматривались более простые системы, но иерархический подход лучше соответствует organizational structure.

##### 7.5.3. Multi-tenancy на уровне инфраструктуры

**Выбранное Решение:** **Soft multi-tenancy** с изоляцией на нескольких уровнях.
**Реализация:**
* Изоляция на уровне: network (Calico network policies), storage (dedicated S3 buckets), compute (node affinity)
* Единый control plane с изолированными data planes
* Мониторинг потребления ресурсов и cross-tenant impact
* Защита от "noisy neighbor" через QoS classes и resource limits

**Обоснование:** Баланс между изоляцией и эффективностью использования ресурсов.

**Компромиссы:** Более сложная конфигурация по сравнению с full isolation.

#### **7.6. Мониторинг качества ML-моделей**

##### 7.6.1. Метрики качества моделей в продакшене

**Выбранное Решение:** Комплексная система мониторинга **ML-specific метрик**.

**Реализация:**
* **Технические метрики:** latency, throughput, error rate, GPU utilization
* **Бизнес-метрики:** accuracy, precision, recall, F1-score (где применимо)
* **Data metrics:** input data distribution, outlier detection
* **Custom метрики:** специфичные для конкретных моделей и use cases

**Обоснование:** Полная видимость работы моделей в production environment.

**Компромиссы:** Накладные расходы на сбор и хранение метрик.

##### 7.6.2. Обнаружение дрейфа данных и концептов

**Решение:** Автоматическое обнаружение дрейфа через **статистические тесты**.
**Реализация:**
* **Data Drift:** KL-divergence, PSI для сравнения распределений входных данных
* **Concept Drift:** мониторинг изменения accuracy и других performance metrics
* **Ансамбль детекторов:** комбинация статистических и ML-based подходов
* **Adaptive thresholds:** автоматическая настройка порогов обнаружения

 **Обоснование:** Раннее обнаружение проблем до значительной деградации качества.

**Альтернативы:** Рассматривались rule-based подходы, но statistical методы более robust.

##### 7.6.3. Автоматические механизмы оповещения о деградации моделей

**Решение:** Многоуровневая система алертинга с **автоматическими действиями**.

**Реализация:**
* **Уровни серьезности:** warning → critical → emergency
* **Каналы уведомлений:** RocketChat
* **Автоматические действия:** автоматическое rollback на предыдущую версию модели
* **Runbooks:** автоматизированные процедуры диагностики и восстановления

 **Обоснование:** Минимизация времени простоя и impact на бизнес.
 
 **Компромиссы:** Риск false positive срабатываний и автоматических действий.
