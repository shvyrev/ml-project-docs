### **8. Кросскатные требования (Cross-Cutting Concepts)**

Данный раздел описывает сквозные аспекты системы, которые влияют на несколько компонентов и требуют единообразного подхода к реализации.

#### **8.1. Аспекты безопасности**

##### 8.1.1. Аутентификация и авторизация

**Выбранное Решение:** Единая интеграция с Keycloak через OIDC протокол.

**Реализация:**
* Все микросервисы используют общий библиотечный модуль `security-oidc-starter`
* JWT токены верифицируются на уровне API Gateway и передаются в сервисы в заголовках
* Ролевая модель RBAC реализована через аннотации `@RolesAllowed` в REST-контроллерах
* Для административных операций требуется роль `system-admin`
* Для пользовательских операций проверяется соответствие `userId` в токене и запросе

##### 8.1.2. Валидация входных данных
 
 **Выбранное Решение:** Jakarta Bean Validation с кастомными валидаторами.
 
 **Реализация:**
* Все DTO аннотируются стандартными (`@NotBlank`, `@Size`) и кастомными валидациями
* Созданы специализированные валидаторы: `@ValidArtifactPath`, `@ValidModelType`
* Глобальный обработчик `@ServiceExceptionMapper` возвращает стандартизированные ошибки валидации
* Валидация схемы входных данных для инференса выполняется автоматически на основе метаданных модели

##### 8.1.3. Санитизация данных

**Решение:** Защита на нескольких уровнях с помощью ORM и специализированных утилит.

**Реализация:**
* **SQL injection:** Защита через использование Hibernate ORM и параметризованных запросов
* **NoSQL injection:** Валидация входных данных перед формированием JSON-запросов
* **Log injection:** Использование структурированного логирования в JSON-формате
* **XSS prevention:** Санитизация HTML-контента через библиотеку OWASP Java Encoder

##### 8.1.4. Ролевая модель и управление доступом (RBAC)

**Решение:** Иерархическая ролевая модель (Role-Based Access Control) с предопределенными ролями и разрешениями.

**Реализация:**
**Роли и привилегии:**
* **Data Scientist:** Полные права на управление своими ресурсами
  * `upload_file`: Загрузка файлов в Artifact Store
  * `register_model`: Регистрация модели в Model Registry
  * `update_model`: Изменение метаданных своих моделей
  * `delete_model`: Удаление своих моделей и их версий
  * `create_endpoint`: Создание эндпоинта для развёртывания
  * `delete_endpoint`: Удаление своих эндпоинтов
  * `deploy_model_version`: Развёртывание своих версий моделей на эндпоинты
  * `run_inference`: Отправка запросов на инференс

* **System Administrator:** Расширенные права для управления платформой
  * `manage_model_garden`: Управление предустановленными моделями в Model Garden
  * `delete_any_model`: Удаление любой модели и её версий
  * `delete_any_endpoint`: Удаление любого эндпоинта
  * `run_inference`: Отправка запросов на инференс к любому эндпоинту

* **Authenticated User:** Базовые права на взаимодействие с публичными ресурсами
  * `run_inference`: Отправка запросов на инференс к любому эндпоинту

*  **Изоляция:** Пользователи имеют доступ только к своим собственным ресурсам (моделям, датасетам, эндпоинтам)
* **Управление:** Роли и привязка пользователей к ролям управляются в Keycloak. Сервисы платформы проверяют JWT-токен, который содержит утверждения (`realm_access.roles`) о ролях пользователя

#### **8.2. Логирование и трассировка**

##### 8.2.1. Структурированное логирование

**Выбранное Решение:** Единый формат JSON с обязательными полями.

**Реализация:**
* Использование Logback с JSON-форматированием
* Обязательные поля в каждом логе: `timestamp`, `service`, `level`, `correlationId`, `userId`, `message`
* MDC (Mapped Diagnostic Context) для автоматического добавления `correlationId` и `userId`
* Интеграция с Loki для централизованного сбора и анализа логов

##### 8.2.2. Распределенная трассировка
*   **Решение:** OpenTelemetry для сквозной трассировки.
*   **Реализация:**
    *   Автоматическое распространение trace context через HTTP-заголовки и Kafka-сообщения
    *   Интеграция с Jaeger для визуализации трассировок
    *   Кастомные атрибуты трассировки для ML-специфичных метрик (modelId, inferenceTime)
    *   Sampling настроен на 100% для ошибок и 10% для успешных запросов

**8.2.3. Уровни логирования**
*   **Решение:** Детализированная политика логирования для разных окружений.
*   **Реализация:**
    *   **PROD:** WARN, ERROR + выборочно INFO для бизнес-событий
    *   **QA:** INFO, WARN, ERROR
    *   **DEV:** DEBUG, INFO, WARN, ERROR
    *   Динамическое изменение уровней логирования через централизованную конфигурацию

#### **8.3. Конфигурация**

##### 8.3.1. Управление конфигурацией

**Выбранное Решение:** Иерархическая система конфигурации с приоритетом внешних источников.

**Реализация:**
* Порядок приоритета: OpenBao Secrets → Kubernetes ConfigMaps → профильные файлы → значения по умолчанию
* Автоматическое обновление конфигурации без перезапуска сервисов
* Валидация конфигурации при старте приложения

##### 8.3.2. Профили конфигурации

**Выбранное Решение:** Application Profiles для environment-specific конфигурации.

**Реализация:**
* `application-dev.yml` - для разработки, с подробным логированием и отладочной информацией
* `application-qa.yml` - для тестирования, с интеграцией в тестовое окружение
* `application-prod.yml` - для продакшена, с оптимизацией производительности и безопасности

##### 8.3.3. Безопасность конфигов

**Решение:** Централизованное управление секретами через OpenBao.

**Реализация:**
* Все чувствительные данные (пароли, ключи API) хранятся в OpenBao
* Автоматическая ротация секретов через политики OpenBao
* Интеграция с Kubernetes через vault-agent-injector для автоматического монтирования секретов
* Аудит доступа к секретам с детализированным логированием

#### **8.4. Обработка ошибок**

##### 8.4.1. Единый формат ошибок
* **Решение:** Стандартизированный JSON-формат для всех ошибок API.
* **Реализация:**
    ```json
    {
      "timestamp": "2023-10-05T12:34:56.789Z",
      "code": 404,
      "message": "Not Found"
    }
    ```

##### 8.4.2. Глобальный обработчик исключений

**Выбранное Решение:** Централизованная обработка исключений через `@ServiceExceptionMapper`.

**Реализация:**
* Единые обработчики для разных типов исключений: `ModelNotFoundException`, `ValidationException`
* Маппинг исключений в соответствующие HTTP-статусы
* Логирование ошибок с полным контекстом для упрощения отладки
* Поддержка перевода сообщений об ошибках для интернационализации

##### 8.4.3. Классификация ошибок

**Выбранное Решение:** Иерархия бизнес-исключений с четкой семантикой.

**Реализация:**
* **Business exceptions:** `ModelNotFoundException`, `EndpointNotFoundException`
* **Validation exceptions:** `InvalidModelException`, `InvalidInputException`
* **Infrastructure exceptions:** `StorageUnavailableException`, `KubernetesClientException`
* Каждое исключение содержит код ошибки и параметризованное сообщение

#### **8.5. Кэширование**

##### 8.5.1. Стратегия кэширования

**Выбранное Решение:** Многоуровневое кэширование с использованием Caffeine и Infinispan.

**Реализация:**
* **L1 (Local):** Caffeine cache для часто запрашиваемых данных (метаданные моделей)
* **L2 (Distributed):** Redis для разделяемого кэша между репликами сервисов
* **HTTP caching:** ETag и Last-Modified заголовки для кэширования ответов API
* **Hibernate L2 cache:** Кэширование сущностей и запросов к БД

##### 8.5.2. Инвалидация кэша*

**Выбранное Решение:** Event-driven инвалидация кэша через Kafka-события.

**Реализация:**
* При изменении данных сервис публикует событие `CacheInvalidationEvent`
* Все сервисы-потребители получают событие и инвалидируют соответствующие кэши
* TTL-based инвалидация для данных, которые меняются редко
* Ручная инвалидация через административный API для экстренных случаев

#### **8.6. Интернационализация (i18n)**

##### 8.6.1. Поддержка multiple языков

**Выбранное Решение:** MessageSource с поддержкой нескольких языков.

**Реализация:**
* Файлы сообщений для русского, английского и других языков СНГ
* Автоматическое определение языка по заголовку `Accept-Language`
* Возможность принудительного выбора языка через query-параметр `?lang=ru`
* Перевод сообщений об ошибках, уведомлений и интерфейса администратора

##### 8.6.2. Форматирование данных

**Выбранное Решение:** Локализированное форматирование дат, чисел и валют.

**Реализация:**
* Использование `LocaleContextHolder` для определения локали
* Автоматическое форматирование дат и чисел в соответствии с локалью
* Поддержка разных форматов дат для разных регионов (DD.MM.YYYY vs YYYY-MM-DD)

#### **8.7. Единые стандарты кодирования**

##### 8.7.1. Code Style и статический анализ

**Выбранное Решение:** Единые стандарты кодирования с автоматической проверкой.

**Реализация:**
* Checkstyle configuration с правилами кодирования
* Spotless plugin для автоматического форматирования кода
* Pre-commit hooks для проверки code style
* Интеграция с CI/CD pipeline для обязательной проверки

##### 8.7.2. API Design Guidelines

**Выбранное Решение:** Единые стандарты проектирования REST API.

**Реализация:**
*   RESTful naming conventions для ресурсов
*   Стандартные HTTP-статусы для разных сценариев
*   Пагинация через `page` и `size` параметры
*   Сортировка через `sort` параметр с поддержкой multiple fields
*   Версионирование API через URL path (`/api/v1/...`)
