### **5. Модель развертывания**

Этот раздел описывает, как наши микросервисы развёртываются, масштабируются и управляются в кластере Kubernetes. Наша модель развёртывания основана на принципах **GitOps**, что обеспечивает автоматизацию и надёжность.

#### **5.1. Ресурсы Kubernetes**

Каждый наш микросервис развёртывается с использованием стандартных объектов Kubernetes.

| **Микросервис** | **Тип K8s-ресурса** | **Назначение** |
| :--- | :--- | :--- |
| **Model Registry** | `Deployment` или `StatefulSet` | Управление экземплярами сервиса. Используется для хранения метаданных о моделях и их версиях. |
| **Artifact Store** | `Deployment` | Управление экземплярами сервиса для работы с файлами. |
| **Сервис инференса** | `Deployment`, `StatefulSet` | Развертывание моделей для инференса. Потенциально может быть заменён на **Knative Service** для оптимизации ресурсов. |
| **Очередь Kafka** | `StatefulSet` | Управление брокером сообщений для асинхронного взаимодействия. |

Для доступа к нашим сервисам и внешним зависимостям мы используем:
* `Service`: Обеспечивает внутреннее обнаружение сервисов и балансировку нагрузки.
* `Ingress`: Управляет внешним доступом к нашим API.
* `Job`: Используется для выполнения одноразовых задач, таких как копирование файлов между хранилищами.
* `ConfigMap` и `Secret`: Хранят конфигурации и чувствительные данные. При этом для секретов используется внешнее корпоративное хранилище **OpenBao**, что обеспечивает повышенный уровень безопасности.

#### **5.2. Сценарий развёртывания**

Процесс развертывания полностью автоматизирован и следует парадигме **GitOps**. 

1.  **Коммит кода**: Разработчик вносит изменения в код и коммитит их в репозиторий **GitLab**.
2.  **CI/CD-пайплайн**: Запускается автоматический пайплайн **GitLab CI/CD**, который выполняет следующие шаги:
    * **Проверки**: Код проходит статические проверки (`lint`), тесты и сканирование на уязвимости.
    * **Сборка**: Происходит компиляция кода и сборка Docker-образа.
    * **Публикация**: Docker-образ публикуется в корпоративном реестре.
3.  **Flux 2**: Инструмент **Flux 2** постоянно отслеживает изменения в репозитории GitLab. Как только новый образ или манифест появляется, Flux 2 автоматически синхронизирует его с состоянием кластера **Kubernetes**.
4.  **Развёртывание в K8s**: Flux 2 применяет необходимые манифесты (`Deployment`, `Service` и т.д.), и Kubernetes развёртывает обновлённые контейнеры.

#### **5.3. Управление ресурсами**

Управление ресурсами осуществляется с помощью **Resource Quotas** в Kubernetes, которые позволяют пользователям самостоятельно определять необходимое количество CPU и RAM для каждого развёртывания.

* Пользователь указывает требования к ресурсам (например, CPU и Memory) для своей модели.
* Система проверяет доступность ресурсов и при необходимости оповещает пользователя, если лимит исчерпан.

Этот подход даёт пользователю гибкость и контроль, при этом обеспечивая эффективное управление ресурсами на уровне всего кластера.

#### **5.4. Специфические требования к сервисам**

* **Artifact Store**: Для этого сервиса требуется **персистентное хранилище** (Persistent Storage) для **MinIO**. Поскольку большие файлы загружаются по частям (`chunks`), хранилище должно быть достаточно быстрым и надёжным. Размер чанков в 5 МБ требует от системы быстрой обработки и пересылки данных.
* **Сервис инференса**: В будущем мы планируем использовать **Knative** для инференса, что позволит нам использовать **Zero-Scaling**, то есть, когда сервис не используется, он не потребляет ресурсов. Это обеспечит значительную экономию.
